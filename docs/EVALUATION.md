# Evaluation methodology

The evaluation view exists to answer four questions with measurements taken from the running
prototype, not from illustrative constants:

1. Does the engine separate labelled attacks from legitimate sessions?
2. How often does it inconvenience legitimate users?
3. How much latency does continuous verification add?
4. Does the decision plane remain available while doing so?

## 1. Corpus

Each evaluation run builds a fresh labelled corpus:

- **Normal sessions** — 140 by default, generated by `simulator.run_normal()`. Resource and
  device choices follow the identity's role, hours cluster around the working day, geolocation
  is local, request rates are modest, and egress is small. The generator is seeded for the
  evaluation path so results are reproducible.
- **Attack sessions** — all 12 scenarios × 3 variants by default. Variants perturb the scenario
  context deterministically (for example IP octet, request count or egress volume) so a lucky
  single request cannot define the result.

The evaluation calls the **live** risk engine but passes `persist=False`, so the operational
event log is not polluted by scoring traffic. The run's aggregate metrics are stored in
`eval_runs` with the thresholds in force at the time.

## 2. Positive class and decisions

The binary positive class is "the engine did not Allow":

```
predicted positive = decision ∈ {CHALLENGE, RESTRICT, BLOCK}
actual positive    = ground_truth == 1 (attack scenario)
```

This is the correct operational definition for a risk-adaptive system: a Challenge is not a
grant, it is a verification gate, so treating it as "not allowed through" is the conservative
choice. The evaluation also reports **containment** separately — the primary variant being
Restrict or Block — because a challenge-only response may be sufficient for low-severity
attacks.

## 3. Metrics

From the confusion matrix:

| Metric | Definition |
| --- | --- |
| Accuracy | `(TP + TN) / total` |
| Precision | `TP / (TP + FP)` |
| Recall / detection rate | `TP / (TP + FN)` |
| F1 | Harmonic mean of precision and recall |
| False-positive rate (FPR) | `FP / (FP + TN)` on legitimate sessions |
| False-negative rate (FNR) | `FN / (FN + TP)` on attacks |

The anomaly detector is scored **separately** against the same ground truth at its own threshold.
This isolates model quality from policy escalation: a low anomaly FNR with a high overall
detection rate shows the contextual rules and policy layer are doing useful work.

## 4. Latency and overhead

All timings are wall-clock measurements in the same process:

- **Decision latency** — time inside `risk.evaluate()`, including database reads, model scoring,
  policy evaluation and event persistence. Average, p50, p95 and maximum are reported.
- **Authentication overhead** — average time for PBKDF2-SHA256 verification at the configured
  work factor, measured over several verifications. This is the dominant cost of a login, not of
  each request (sessions are token-based).
- **Protected-service latency** — a representative read-only database query and JSON
  serialisation, measured over several rounds.

These are single-host, single-process measurements. They are useful for relative comparisons
(normal vs. attack conditions, configuration changes) but are not production SLAs. Network,
TLS, external IdP and SIEM costs are absent by construction.

## 5. Availability

```
availability = (requests that produced a decision without an engine error) / total requests
```

An engine error is an exception raised by the scenario runner. The prototype does not inject
faults, so a healthy run reports 100%; the metric is included because the brief asks for
availability and because it makes regressions visible if a code change breaks a scenario.

## 6. Reproducing a run

From the Evaluation page, press **Run evaluation**. From the API:

```bash
curl -c cookies.txt -X POST http://127.0.0.1:8000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"analyst@hybridcloud.io","password":"Analyst#2026"}'

curl -b cookies.txt -X POST http://127.0.0.1:8000/api/sim/evaluation \
  -H "Content-Type: application/json" \
  -d '{"name":"Reported run","normal_samples":140,"variants":3}'
```

The response contains the full metrics object and a `run_id`. Retrieve it later with
`GET /api/evaluation/runs/{run_id}`. Run history is shown in the Evaluation page; clicking a row
loads that stored run without re-executing the simulation.

The identical evaluation runs once at first startup and is stored as the baseline.

## 7. Interpreting the numbers

- A high detection rate with a low FPR is the useful operating point. Because the corpus is
  synthetic and the normal generator is deliberately well-behaved, reported FPR will be lower
  than a real enterprise baseline.
- If FNR is dominated by one scenario, inspect that scenario's primary decision and signal
  breakdown in the per-scenario table. The most likely causes are a device-trust floor that is
  not being crossed or a context that does not trigger a rule.
- Changing thresholds in the admin console changes subsequent evaluation runs. The stored run
  records the thresholds used, so historical comparisons remain valid.
- Retraining the model changes anomaly metrics but not the policy layer. Evaluate both together:
  a model with a higher anomaly FPR may still produce acceptable overall FPR because policy
  escalation is deterministic.

## 8. Threats to validity

- **Synthetic corpus.** Normal behaviour is generated from assumptions; real traffic has longer
  tails and concept drift.
- **Small attack set.** Twelve techniques with three variants each is enough for a prototype but
  not for statistical confidence.
- **Single host.** Latency excludes network and external identity providers.
- **Seeded data.** Reproducibility is deliberate, but repeated runs will not explore new normal
  behaviour unless the seed or generator changes.
- **Threshold sensitivity.** Detection and FPR trade off directly; the reported point is one
  configuration, not an optimum.
- **No adversary adaptation.** Scenarios are fixed patterns; a real attacker could shape traffic
  to stay under the floors.

These limitations are stated in the UI note and are appropriate for a taught research prototype.

## 9. Effect of the Phase 2.2 security changes

Phase 2.2 changed how step-up challenges are stored and answered, how MFA secrets are stored,
what each role can see and how malformed requests are rejected. It did not change signals,
weights, thresholds, policies, the anomaly model or the scenario generators.

- **Detection metrics are unchanged.** The default evaluation (140 normal sessions, 12
  scenarios × 3 variants) run on fresh databases with the code before Phase 2.2 (`87bacf2`) and
  after it gave identical results: accuracy 0.9261, precision 0.7347, recall 1.0, FPR 0.0929,
  FNR 0.0, decisions ALLOW 127 / CHALLENGE 15 / RESTRICT 10 / BLOCK 24. Evaluation runs use
  `persist = False`, so they create no challenge rows.
- **Simulator traffic is labelled.** Persisted scenario and normal-traffic events, and evaluations
  an operator runs for another identity, carry `simulated = true` in the event APIs. Their
  challenges are simulation challenges that never touch a real identity's MFA state, so running
  the attack lab cannot lock a user out of step-up.
- **Overhead.** Decrypting a TOTP secret (AES-256-GCM) took 4.9 µs on average over 20,000 runs
  on the development machine, once per verification. Persisting a challenge adds one `INSERT`
  to the request that produced the `CHALLENGE`, inside the transaction that already writes the
  event. The challenge insert was not benchmarked separately.
- **Several workers.** Because challenge state is now in SQLite, the prototype can be measured
  with several Uvicorn workers on one host. The latency figures above are still single-process
  measurements.
