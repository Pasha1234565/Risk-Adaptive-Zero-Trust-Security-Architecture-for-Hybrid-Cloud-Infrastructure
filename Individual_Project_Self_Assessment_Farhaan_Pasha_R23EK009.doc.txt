2. MY UNDERSTANDING OF THE PROBLEM
--------------------------------------------------------------------------------

What problem does the project address?
  Hybrid cloud environments combine private and public cloud infrastructure to
  gain scalability, flexibility, and cost efficiency. However, this mix creates
  multiple trust boundaries: users, devices, applications, and resources may sit
  across different networks and providers. Traditional perimeter-based security
  models, which implicitly trust anything inside the network, cannot safely cover
  such a distributed environment. The project addresses this gap by designing a
  security architecture that does not assume internal users or devices are safe
  by default.

Why is this problem important?
  As organizations increasingly adopt hybrid-cloud strategies, the attack surface
  grows. A compromised credential, a misconfigured VM, or an unusual access
  pattern inside what was "trusted" can lead to data exposure or lateral movement.
  Static, rule-based access control is too rigid to catch these subtle risks and
  too blunt to avoid disrupting legitimate work. A risk-adaptive, Zero-Trust
  approach is important because it continuously evaluates each access request
  against identity, device, behavioural, and resource context, then adapts its
  response based on the current risk level.

Who or what will benefit from the proposed solution?
  - The organization operating the hybrid cloud, by reducing the chance of
    unauthorized access, lateral movement, and data leakage.
  - End users and administrators, by receiving access decisions that reflect the
    real risk of a request rather than blanket restrictions.
  - The research and academic community, through a working prototype and
    quantitative evaluation (detection accuracy, false-positive/negative rates,
    authentication overhead, and service latency).
  - Team members, by gaining hands-on experience in cloud infrastructure,
    identity and access management, anomaly detection, and security evaluation.

What are the major challenges involved?
  - Designing a hybrid cloud topology that is realistic yet safe and well
    controlled for experimentation.
  - Collecting enough behavioural data to establish reliable baselines for normal
    access patterns.
  - Choosing and tuning anomaly-detection techniques so they catch suspicious
    behaviour without generating excessive false positives.
  - Combining multiple contextual signals (identity, device, behaviour, resource,
    request characteristics) into a risk score that maps cleanly to Allow,
    Challenge, Restrict, or Block decisions.
  - Balancing security responsiveness with service latency and authentication
    overhead so the system remains usable.
  - Conducting attack simulations ethically and only inside the authorized
    project environment.

3. MY UNDERSTANDING OF THE PROPOSED SOLUTION
--------------------------------------------------------------------------------

What do I think the proposed system will do?
  The system will act as a Zero-Trust access-control layer for a hybrid cloud
  environment. Every access request will be authenticated, then continuously
  evaluated using multiple contextual signals. Based on a calculated risk score,
  the system will decide to Allow (low risk), Challenge (medium risk), Restrict
  (high risk), or Block (critical risk) the request. It will also monitor
  behaviour over time, detect anomalies, and feed those anomaly scores back into
  the risk engine.

What are the major components or modules?
  1. Hybrid cloud environment (private + public cloud resources, VMs/instances,
     controlled communication layer, documented topology).
  2. Identity and Zero-Trust access control (authentication, least-privilege
     policies, per-resource access rules).
  3. Behavioural data collection (logs of login time, access frequency, resource
     usage, device/session context, normalized for analysis).
  4. Behavioural anomaly detection (baseline profiles, trained model,
     anomaly scoring).
  5. Risk-adaptive access-control engine (integrates identity, device, anomaly
     score, requested resource, request characteristics, and current security
     context into a risk decision).
  6. Security monitoring and attack simulation (centralized logging, controlled
     suspicious scenarios, observation of system responses).
  7. Performance and security evaluation (accuracy, false-positive/negative
     rates, authentication overhead, latency, availability).

How do I think these components will work together?
  A user or device initiates an access request, which goes through authentication
  first. After authentication, the system collects context about the request and
  the session. That context is compared against behavioural baselines using the
  anomaly-detection module, which produces an anomaly score. The risk engine
  combines the identity/privilege information, device context, anomaly score,
  requested resource, request characteristics, and current security context into
  an overall risk level. The policy engine then issues an Allow / Challenge /
  Restrict / Block decision. Meanwhile, centralized logging and monitoring record
  normal and simulated attack scenarios so the team can observe and evaluate how
  the system responds.

What is my current understanding of the overall workflow?
  User / Device → Authentication → Context Collection → Anomaly Detection →
  Risk Score → Policy Engine → Access Decision

In my own words, the workflow is: a request arrives, the system verifies who is
making it and under what conditions, compares that request to learned normal
behaviour, computes a risk level, and then chooses an adaptive response rather
than a one-size-fits-all rule. The prototype will also be tested against
controlled attack scenarios so the team can measure how well detection and access
decisions perform under both normal and suspicious conditions.
